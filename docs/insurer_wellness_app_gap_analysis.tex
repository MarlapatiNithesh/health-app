% --- 2. System Context & Topology Comparison ---
\section{System Context \& Topology Comparison (PDF Section 1)}

\subsection{Architectural Blueprint Specification (Figure 1 \& Figure 3)}
The blueprint specifies an enterprise-grade Insurer Wellness Platform connected across four core tiers:
\begin{enumerate}[leftmargin=1.5em]
    \item \textbf{Client Actors:} Member Mobile (Flutter), Guest User, Corporate Admin, Internal Admin, and Clinical Reviewer.
    \item \textbf{Backend Core:} API Platform exposing REST/GraphQL, supported by an event broker and an Analytics Data Warehouse.
    \item \textbf{External Integration Gateway:} Real-time integration to Policy Administration, Read-only Claims SSO, Underwriting batch extract, CRM two-way sync, Broker aggregate API, TPA data sharing, and Finance monthly reconciliation.
    \item \textbf{Third-Party Providers:} Wearables (Apple Health, Google Health Connect, Garmin, Fitbit, Whoop, Oura), Push/SMS gateways, and Reward Voucher Partners.
\end{enumerate}

\subsection{Current Codebase Implementation Status}
\begin{statusbox}[Architecture Reality: In-Process High-Throughput Modular Monolith]{accentteal}
    Rather than deploying 12 physically distributed microservices requiring complex Saga orchestrations during early development, the engineering team has constructed a \textbf{cohesive, layered in-process modular monolith} built in Node.js (ESM) with native PostgreSQL 16+ and pgvector.
\end{statusbox}

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{API Gateway \& Routing Layer:} \textcolor{statuscompleted}{\textbf{COMPLETED (100\%)}}. Implemented via Express 5.1 in \texttt{src/app.js}. Provides unified reverse-routing, CORS handling, structured JSON logging, global error normalization (\texttt{ApplicationError}), request ID tracking, and Swagger OpenAPI documentation (\texttt{/docs}).
    \item \textbf{Identity \& Communications Provider:} \textcolor{statuscompleted}{\textbf{COMPLETED (100\%)}}. Implemented via \texttt{TwilioVerifyClient} (\texttt{src/integrations/twilio-verify-client.js}), supporting SMS, WhatsApp, and dev-mode verification.
    \item \textbf{Wearable Gateway:} \textcolor{statuscompleted}{\textbf{COMPLETED (100\%)}}. Implemented via \texttt{OpenWearablesClient} (\texttt{src/integrations/open-wearables-client.js}) and Svix-validated webhooks (\texttt{src/routes/webhook-routes.js}).
    \item \textbf{Core Insurance Adapters:} \textcolor{statusnotstarted}{\textbf{NOT YET STARTED (0\%)}}. No connectors currently exist in \texttt{src/integrations/} for Policy Admin, Claims, Underwriting, or TPA systems.
    \item \textbf{Analytics Warehouse:} \textcolor{statusnotstarted}{\textbf{NOT YET STARTED (0\%)}}. No external warehouse ETL pipeline is configured; operational metrics rely on PostgreSQL views (\texttt{v\_timeline}) and direct aggregation queries.
\end{itemize}

% --- 4. Detailed Workflow & Use Case Comparison ---
\section{Detailed Workflow \& Use Case Audit}

\subsection{UC-01: OTP Authentication (Figure 9)}
\begin{statusbox}[Implementation Status: COMPLETED (100\%)]{statuscompleted}
    \textbf{Specification:} Member submits phone $\to$ Gateway validates rate-limit $\to$ Identity requests OTP via Provider $\to$ OTP Store saves hash with TTL $\to$ User submits code $\to$ Identity validates attempts/TTL $\to$ Session tokens issued $\to$ Audit logged.
\end{statusbox}
Fully implemented across \texttt{phone-routes.js}, \texttt{PhoneVerificationService}, and \texttt{PhoneVerificationRepository}. Rate limiting enforced via middleware and 60-second cooldown in \texttt{phone\_verification\_sessions}. Returns signed JWT access token and auto-provisions \texttt{members} and \texttt{patients} records.

\subsection{UC-02: Policy Linking (Figure 11)}
\begin{statusbox}[Implementation Status: NOT YET STARTED (0\%)]{statusnotstarted}
    \textbf{Specification:} Member enters policy number + DOB $\to$ Gateway authorizes $\to$ MemberService delegates to PolicyAdapter $\to$ Policy Administration verifies eligibility $\to$ Returns normalized coverage $\to$ Persists PolicyLink $\to$ Publishes \texttt{POLICY\_LINKED} event.
\end{statusbox}
No policy routing or external insurance adapter exists. Members currently have an \texttt{insurance\_tier} dynamically calculated from wellness telemetry rather than linked to an underwritten commercial policy.

\subsection{UC-03: Complete Onboarding (Figure 10)}
\begin{statusbox}[Implementation Status: COMPLETED (100\%)]{statuscompleted}
    \textbf{Specification:} Save profile/goals/lifestyle $\to$ Record consent versions $\to$ Link policy $\to$ Calculate initial score $\to$ Emit \texttt{MEMBER\_ONBOARDED}.
\end{statusbox}
Profile update (\texttt{PATCH /v1/me/profile}), biometric history tracking (\texttt{member\_biometric\_history}), and consent recording (\texttt{POST /v1/me/consents}) are fully operational in the codebase.

\subsection{Account Deletion Lifecycle (Figure 12)}
\begin{statusbox}[Implementation Status: COMPLETED (100\%)]{statuscompleted}
    \textbf{Specification:} REQUESTED $\to$ VALIDATING $\to$ APPROVED $\to$ PROCESSING $\to$ COMPLETED.
\end{statusbox}
\texttt{DELETE /v1/me} calls \texttt{MemberService.deleteAccount()}, deletes the remote OpenWearables account to cease vendor streaming, and soft-deletes the local member record (\texttt{status='deleted'}).

\subsection{UC-04: Wearable Synchronization (Figure 14)}
\begin{statusbox}[Implementation Status: COMPLETED (100\%)]{statuscompleted}
    \textbf{Specification:} Scheduler/Webhook $\to$ Sync Queue $\to$ Provider Adapter $\to$ Fetch delta/webhook $\to$ Normalize units/timezones $\to$ Validate + deduplicate + provenance $\to$ Insert timeseries $\to$ Update cursor $\to$ Emit \texttt{HEALTH\_METRICS\_INGESTED}.
\end{statusbox}
Implemented via \texttt{WebhookService} and \texttt{HealthService}. Handles Svix-validated webhooks from OpenWearables (Garmin, Fitbit, Apple Health) and batch uploads from phone health SDKs, storing metrics into \texttt{workouts}, \texttt{sleep\_sessions}, \texttt{womens\_health}, and \texttt{timeseries}.

\subsection{Health Score Calculation (Figure 15)}
\begin{statusbox}[Implementation Status: COMPLETED (100\%)]{statuscompleted}
    \textbf{Specification:} Load ScoreConfig $\to$ Collect activity, sleep, vitals, nutrition, habits, risks $\to$ Calculate weighted contributions $\to$ Aggregate score $\to$ Persist HealthScore $\to$ Emit \texttt{SCORE\_UPDATED}.
\end{statusbox}
\texttt{WellnessService.calculateWellnessMetrics()} queries 48-hour sleep duration, current-day steps, and HRV to assign scores (0--100) and insurance tiers (Bronze, Silver, Gold, Platinum).

\subsection{UC-05 to UC-08: Gamification, Challenges \& Rewards}
\begin{statusbox}[Implementation Status: NOT YET STARTED (0\%)]{statusnotstarted}
    \textbf{Specification:} Habits (UC-05), Quizzes (UC-06), Challenges (UC-07), and Reward Redemption (UC-08).
\end{statusbox}
These gamification and points-ledger workflows have not yet been developed in the repository.

% --- 5. Extended Capabilities: MediBot Clinical Suite ---
\section{Extended Capabilities: MediBot Clinical Intelligence Suite}

While the codebase currently focuses on health telemetry and omits casual gamification habits, it contains an advanced \textbf{Clinical AI \& Document Intelligence Engine} that operates at 100\% completion:

\begin{statusbox}[Implementation Status: COMPLETED (100\%)]{statuscompleted}
    \textbf{MediBot Clinical Intelligence Suite:} Full clinical record tracking, multimodal OCR, biomedical entity extraction, and clinical safety triage.
\end{statusbox}

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Patient 360 Core:} Longitudinal store for medical conditions, prescriptions, medication events, allergies, and diagnostic lab results with start/end timestamps and verification statuses (\texttt{clinical\_records}).
    \item \textbf{Multimodal Document Intelligence:} Ingestion of prescription images and lab reports with SHA-256 and visual block hashing. Transcribes via Gemini Vision API with Tesseract.js fallback (\texttt{DocumentService}).
    \item \textbf{Biomedical NER Microservice:} Python FastAPI service running scispaCy (\texttt{scispacy\_en\_core\_sci\_sm}) extracts medication names, dosages, frequencies, and lab markers.
    \item \textbf{Confidence Gating \& Auto-Commit:} Extracted entities with confidence $\ge 0.85$ are automatically written to \texttt{clinical\_records}.
    \item \textbf{Clinical Safety Rules:} Pre-screens acute medical emergencies (chest pain, stroke symptoms), checks drug-drug interactions using deterministic pharmacopeia rules and live OpenFDA queries, and checks allergy contraindications.
    \item \textbf{Adaptive Symptom Assessment:} Multi-turn clinical inquiry systematically gathers symptom onset, duration, severity, and relieving factors (\texttt{symptom\_assessments}).
    \item \textbf{RAG Semantic Search:} Text chunks and medical guidelines are embedded into 768-dimensional vectors in \texttt{clinical\_embeddings} and indexed with pgvector IVFFlat cosine search.
\end{itemize}

\section{Prioritized Engineering Roadmap}

To build the remaining features that are \textbf{Not Yet Started}, the following engineering sprints are scheduled:

\subsection{Phase A: Policy Linking \& Core Insurance Adapters}
\begin{itemize}[leftmargin=1.5em]
    \item Create database table \texttt{policy\_links} with foreign keys to \texttt{members(id)}, storing policy number, insurer code, coverage dates, and status.
    \item Implement \texttt{PolicyAdapter} interface in \texttt{src/integrations/policy-adapter.js} to communicate with external core policy administration APIs.
    \item Expose \texttt{POST /v1/me/policy/link} and \texttt{GET /v1/me/policy/status}.
\end{itemize}

\subsection{Phase B: Gamification, Habits \& Points Ledger}
\begin{itemize}[leftmargin=1.5em]
    \item Create database tables \texttt{habits}, \texttt{habit\_logs}, \texttt{challenges}, \texttt{challenge\_participants}, \texttt{points\_ledger}, and \texttt{reward\_catalog}.
    \item Implement \texttt{HabitService} supporting daily check-ins, streak computation, and points triggering (\texttt{POST /v1/me/habits/:id/complete}).
    \item Build an immutable double-entry \texttt{PointsLedgerService} ensuring ACID transactions for point credits and reward redemptions.
\end{itemize}

\subsection{Phase C: Admin Panel, B2B Corporate Anonymity \& CMS}
\begin{itemize}[leftmargin=1.5em]
    \item Implement corporate tenant routing (\texttt{/v1/corporate/dashboard}) enforcing the strict $k \ge 20$ cohort threshold for privacy compliance.
    \item Build content approval workflow (Draft $\to$ Clinical Review $\to$ Published) for educational wellness content.
\end{itemize}
